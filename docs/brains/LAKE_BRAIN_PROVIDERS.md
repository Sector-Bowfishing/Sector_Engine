## 2. Traps the adapters enforce

| Trap | Handling |
|---|---|
| USGS `00065` is a gage height in a local datum, not an elevation | refused as a live series; as a history only with an explicit datum offset (gage height + site altitude, Lake Winnebago) |
| A recorded datum offset must apply whatever the provider | one sign convention: the offset is **added** to the reading (`archived = reading + offsetFt`, `current = reading + datumOffsetFt`). Live: the classifier adds `datumOffsetFt` for every provider. History: `usgsDaily`, `hadsDaily`, `cdecDaily` readers add their case's `offsetFt`; for `cwmsDaily`, `riseDaily`, `tvaOperatingGuide`, `coopsDaily`, `usgsStageDaily` the runner adds the generated record's `offsetFt` (`LakeHistoryOffsets.swift`, 2026-11-22; before that it was silently dropped). Offset 0 leaves rows unchanged |
| USGS `-999999` no-data sentinel (a sensor outage today at Buckeye Lake) | dropped; the lake falls back and says so (`primarySourceStale`, `fallbackSource`) |
| CWMS defaults to SI units | requested with `unit=EN`; a response that still says metres is multiplied by 3.28084 |
| CWMS dense series (15 min) overflow the page budget | request window shrinks with the series interval (5 years daily/hourly, about 1 year at 15 min); hitting the 20-page limit is an error, never a silent truncation |
| Sub-daily history series | reduced to the median of each lake-local day (identical to the reading itself for a daily series) |
| Access2Water plain `Elev` on tailwater locations looks like a pool | bindings carry the exact tsid; the tailwater sibling is a different tsid and is never read |
| Access2Water is latest-only | the reading is the latest value and, from `delta24hr`, the value 24 h earlier: enough for the 24 h trend, 1 h / 6 h / 3 d / 7 d changes stay unknown |
| RISE writes 0.0 for a missing day; results can be modeled | `result <= 0` and any `resultType` other than `observed` dropped; the history day is the UTC date of the stamp (as in the research) |
| NWPS `HG` stage vs `HP` pool; `-999` sentinels; flow units | the gauge's `pedts` must start with the binding's pe code; units must be ft; sentinels dropped |
| IEM HADS rate limit (HTTP 429 above about one request per 15 s) | one process-wide gate (15 s between requests), 3-year chunks newest first, 429 backs off 60 s and doubles; any failed chunk fails the whole pull (no silent hole), the walk stops at the first empty chunk |
| CDEC sensor 15 is storage (acre-feet), sensor 1 a river stage | only sensor 6 (`RES ELE`, reservoir elevation) is read; any other sensor is refused before a request, and an answer whose `units` are not feet fails as a whole |
| CDEC `-9999` missing value is a number, not null (often a third of the rows); 0 is a mechanical error | values <= -9000 and exactly 0 dropped; a day with no reading stays missing, never filled |
| CDEC timestamps have no offset | read as Pacific wall-clock time (America/Los_Angeles, daylight saving applied); daily `D` rows keep the date in their stamp (section 4) |
| CO-OPS `hourly_height` and `daily_mean` are verified-only and lag weeks (both ended 2026-10-31 when read on 2026-11-22) | live is `water_level` only; any other live product is refused before a request. History is verified daily means plus a tail of preliminary `water_level` reduced to lake-local daily medians |
| CO-OPS answers HTTP 200 with `{"error":{"message":…}}`; IGLD exists only at Great Lakes stations | "No data was found" is an empty window; any other message (e.g. a tidal station asked for IGLD) is a failure; a response for another station is refused |
| CO-OPS empty values and quality flags | empty `v` dropped; preliminary rows with the flat-line (F) or limit (L) flag dropped; daily means with the limit (L) flag dropped; rate-of-change (R) kept (a seiche trips it legitimately) |
| USGS `00065` gage height is not an elevation | `usgsStage` adds the site's published altitude (`alt_va`) and refuses when there is none, when `alt_datum_cd` is blank, when it differs from the datum the binding names, or when the gage height is not in feet |
| A research history that is a different series from the live level | every run compares the median of the seeded history of the last 365 days with the live level; more than 15 ft sets `historyLiveMismatch:<delta>ft` and an error. The 14 lakes the rules-v2 QA found are held out of the table |

## 4. CDEC (California DWR) reservoir elevation

Added 2026-11-22. **Reader only:** no lake is bound to CDEC (`LakeBrainCDECTests.testNoLakeIsBoundToCDEC`). Binding a California lake goes through the acceptance gate like every other binding (`LAKE_BRAIN_BINDING_REVIEW_PROTOCOL.md`), and `cdec` is not yet on the bindings-table allow-list (`jobs/lake-brain/bindings/build_bindings_table.py`, Almanor and Berryessa are excluded as `provider-not-allowed`).

- **Source.** California Department of Water Resources, California Data Exchange Center. Endpoint `JSONDataServlet` (above); answer: a JSON array, one object per reading: `stationId`, `durCode`, `SENSOR_NUM`, `sensorType`, `date` and `obsDate` (`yyyy-MM-dd HH:mm`, no offset), `value` (number), `dataFlag`, `units`. Station ids are short codes (`SHA` Shasta, `ORO` Oroville, `FOL` Folsom). No authentication; no published rate limit or quota.
- **Binding shape.** Live: `provider: cdec`, `station` = the CDEC id, `series` = `6` (hourly) or `6:H`, `6:E` (event, about 15 min), `6:D` (daily); `sourceId` `cdec:{ID}:{series}`. History: `cdecDaily(station, sensor, dur, offsetFt)`, in the generated table `{"kind": "cdecDaily", "station", "sensor", "dur", "offsetFt"}`.
- **Cadence.** Hourly (`H`) is the usual reservoir series; event (`E`) exists for some stations; daily (`D`) values go back decades for the large reservoirs. History is pulled newest first in windows of 10 years (`D`), 1 year (`H`) or 60 days (`E`), one request at a time; two empty windows in a row end the walk and any failed window fails the whole pull. A daily value is expected for yesterday (the default `expectedLatestDay`).
- **Time zone.** Stamps carry no offset and are read as Pacific wall-clock time with daylight saving (`LakeFleetClients.cdecTimeZone`). One third-party client documents exactly that (CDEC times "in Pacific Time and Daylight Savings adjustments are reflected"); CDEC's own statement could not be retrieved. If CDEC in fact stamps fixed PST all year, summer readings are read one hour **older** than they are, never fresher, so the freshness rule stays conservative. Confirm on the first live probe (compare a summer hourly stamp with the same reading on the station's CDEC page) before binding a lake.
- **Missing values.** `-9999` (a number) is dropped, as is anything <= -9000 and an exact 0. `dataFlag` is not interpreted; a station that writes a text flag into `value` yields no reading for that row.
- **Datum.** CDEC does not state the vertical datum per series; most projects report in their historical datum (typically NGVD29, not NAVD88). The binding review records the datum and sets `datumOffsetFt` (live) / `offsetFt` (history) when it differs from the lake's pool reference.
- **Health plane.** `cdec` is not yet a declared Lake input (`brain.json` providers, `providers/PROVIDERS.json`, the `lake-brain` job manifest, Swift `BrainOwnership`) and has no source-health record in `LakeBrainRunner.sourceRecords`; that registration belongs with the first accepted CDEC binding (operating contract section 10: new providers need the owner's approval).
- **Access note (owner rule 2026-11-22: no CDEC binding without DWR's written permission).** CDEC's `robots.txt` disallows automated crawling of `/dynamicapp/`; the Brain is not a crawler (it requests named series only, a few requests per lake per run), but the owner should confirm this use before a lake is bound.
- **Tests.** `brains/lake/tests/swift/LakeBrainCDECTests.swift` with `brains/lake/tests/fixtures/cdec/SHA_6_H.json` (shape of the JSONDataServlet answer with a `-9999` row; assembled from the documented format because the host was not reachable from the authoring session, to be replaced by a recorded answer). No test makes a network call.

## 5. NOAA CO-OPS Great Lakes water levels

Added 2026-11-22. **Reader only:** no lake is bound to CO-OPS (`LakeBrainCOOPSTests.testNoLakeIsBoundToCOOPS`). Binding a lake goes through the acceptance gate (`LAKE_BRAIN_BINDING_REVIEW_PROTOCOL.md`), and `coops` is not on the bindings-table allow-list (`jobs/lake-brain/bindings/build_bindings_table.py`).

- **Source.** NOAA National Ocean Service, Center for Operational Oceanographic Products and Services (CO-OPS), Data API `datagetter` (documented at `https://api.tidesandcurrents.noaa.gov/api/prod/`). Answer: `{"metadata":{"id","name","lat","lon"},"data":[{"t","v","s","f","q"}]}`; `t` is `yyyy-MM-dd HH:mm` in the requested time zone, `v` a string (empty when missing), `f` comma-separated 0/1 flags, `q` `p` (preliminary) or `v` (verified). Errors come back as HTTP 200 `{"error":{"message":…}}`.
- **Binding shape.** Live: `provider: coops`, `station` = the 7-digit station id (e.g. `9087044` Calumet Harbor, Lake Michigan), `series` = `water_level` or nil; `sourceId` `coops:{ID}:water_level`. History: `coopsDaily(station)`, in the generated table `{"kind": "coopsDaily", "station"}`.
- **Datum.** Always `datum=IGLD` (International Great Lakes Datum; IGLD (1985) today). IGLD is offered only at Great Lakes stations, so a tidal station is refused by the API. IGLD (2020) is expected to be adopted in the US by 2027 (NOAA IGLD FAQ): when CO-OPS switches, the series will step by the datum change and history on the old datum must not be mixed with the new one. The binding review records the datum; `datumOffsetFt` puts the reading on the lake's pool reference if that differs.
- **Cadence.** `water_level` is 6-minute, preliminary until verified; `range` (hours, at most 744) gives the most recent readings. `hourly_height` and `daily_mean` are verified products updated about monthly: on 2026-11-22 both ended at 2026-10-31 for 9087044, so neither is a live series.
- **History.** Verified daily means (`daily_mean`, Great Lakes only, must be asked in `lst`, so its day is the station's standard-time date; up to 10 years per request), newest first in 10-year chunks, stopping at the first empty chunk; then the days after the last verified mean (at most 93 days back; if the gap to fill is older than that, the pull fails rather than leave a hole) from preliminary `water_level` in 31-day windows, reduced to the median of each lake-local day. Any failed request fails the whole pull. An incremental run (the runner's last 21 days) is usually all preliminary tail; preliminary days already in the archive are not replaced by verified means later (a full backfill does that).
- **Harbour, not lake mean.** A station is one harbour on a very large lake. Wind setup and seiche move it by tenths of a foot within hours, so the 1 h / 6 h changes of a Great Lakes station describe that harbour, not the lake.
- **Access check (owner rule 2026-11-22: use a source only if its terms / robots.txt do not forbid automated reading).** `api.tidesandcurrents.noaa.gov/robots.txt` and `tidesandcurrents.noaa.gov/robots.txt` could not be retrieved from this session (the fetch failed; no content), so no robots rule is known. The NOS disclaimer (`tidesandcurrents.noaa.gov/disclaimers.html`, read 2026-11-22) says information on the government servers is "in the public domain, unless specifically annotated otherwise", asks for attribution when redistributed, and says nothing against automated access. The API documentation itself is written for programmatic clients and asks them to identify themselves (`application`) and to space requests. Nothing found forbids this use; re-check robots.txt before binding a lake.
- **Politeness and terms.** CO-OPS throttles per customer and asks callers to space requests and download only what they need: one request at a time per process, at least 1 s apart, with `application=Sector_LakeBrain` and the Sector-LakeBrain User-Agent. Public US government data; contact `co-ops.userservices@noaa.gov`.
- **Health plane.** `coops` is not yet a declared Lake input (`brain.json` providers, `providers/PROVIDERS.json`, the `lake-brain` job manifest, Swift `BrainOwnership`) and has no source-health record in `LakeBrainRunner.sourceRecords`; that registration belongs with the first accepted CO-OPS binding (operating contract section 10).
- **Tests.** `brains/lake/tests/swift/LakeBrainCOOPSTests.swift` with `brains/lake/tests/fixtures/coops/` (station, keys, flag layout and the values of the unflagged rows read from the live API on 2026-11-22, transcribed rather than captured byte for byte; empty and flagged rows added). No test makes a network call.

## 6. USGS gage height + site altitude (`usgsStage`)

Added 2026-11-22. **Reader only:** no lake is bound to it (`LakeBrainUSGSStageTests.testNoLakeIsBoundToUSGSStage`).

- **Source.** USGS Water Services (the same legacy WaterServices host the `usgs` provider reads): the site service (`/nwis/site/`, RDB, `siteOutput=expanded`) for `alt_va` (altitude of the gage datum), `alt_acy_va` (its accuracy), `alt_datum_cd` (its vertical datum, e.g. `NAVD88`, `NGVD29`) and `site_tp_cd`; the instantaneous-values service for `00065` (gage height, ft).
- **Rule.** Elevation = gage height + `alt_va`, only when the site publishes both `alt_va` and `alt_datum_cd`, only when `alt_datum_cd` is the datum the binding names, and only when `alt_va` is not 0 (an unsurveyed placeholder). An answer with more than one gage-height series for one statistic (sub-locations at a dam, e.g. forebay and tailwater) is refused, live and in history. Otherwise the reading is refused (no fallback to a bare stage).
- **Binding shape.** Live: `provider: usgsStage`, `station` = the USGS site number, `series` = the expected altitude datum (`NAVD88`); `sourceId` `usgs-stage:{site}:00065:{datum}`. History: `usgsStageDaily(site, datum, stat)` (`stat` as `usgsDaily`: `dv` merged daily statistics, a stat code, or `iv` daily medians), in the generated table `{"kind": "usgsStageDaily", "site", "datum", "stat"}`. The altitude is read at run time, so a USGS datum change (USGS has been moving gages from NGVD29 to NAVD88) stops the lake with an error instead of stepping its series. The existing `usgsDaily` with a fixed `offsetFt` (Lake Winnebago) is unchanged.
- **Cadence.** Usually 15-minute readings, about 1 h latency; the site record is read once per site per 15 minutes.
- **Caveats.** The altitude is today's; historical gage heights recorded on an earlier gage datum are shifted by today's altitude, so a gage whose datum moved during its record has a step in its history (the 15 ft history/live mismatch check catches only large ones; the binding review should check the site's datum history). `site_tp_cd` is reported but not enforced; the binding review establishes that the gauge is on the lake. **Legacy host retirement:** the WaterServices home page (read 2026-11-22) says "WaterServices will be permanently shut down on February 22nd, 2027" and that requests will be intentionally slowed, with intentional outages, from January 2027. This reader, like the existing `usgs` provider and the USGS history, must move to the Water Data APIs (`api.waterdata.usgs.gov`) before then; whether the new monitoring-locations collection carries the altitude and its datum was not checked (the host refused the session's fetch).
- **Access check (owner rule 2026-11-22).** `waterservices.usgs.gov/robots.txt` could not be retrieved from this session (the fetch failed; no content). USGS copyrights page (`usgs.gov/information-policies-and-instructions/copyrights-and-credits`, read 2026-11-22): "USGS-authored or produced data and information are considered to be in the U.S. Public Domain." The WaterServices home page describes machine-readable REST services for programs and states no rule against automated access. Nothing found forbids this use (the same host the existing `usgs` provider already reads). No key.
- **Health plane.** As CO-OPS: not yet a declared Lake input and no source-health record; registration belongs with the first accepted binding.

## 8. USGS Water Data API (v1) path for `usgs`, `usgsStage` and the USGS history (switch, default off)

- **Why.** Legacy WaterServices adds a delay to every request from 2026-11-16 (2 s; 10 s from 2027-01-11, beyond the readers' 8 s / 60 s timeouts) and shuts down on 2027-02-22 (migration plan, 2026-11-22). Code: `brains/lake/runtime/LakeBrain/LakeLevelFeedsUSGSWaterData.swift`.
- **Switch.** `LAKE_USGS_API` = `legacy` (default; also unset, empty or unknown), `v1`, or `shadow`. The switch lives in the job environment, not in the packaged knowledge release: the bindings and their release id are unchanged. In `shadow` the legacy answer is the one used and the v1 answer is only compared, one log line per read: `[usgs-shadow] site= param= kind=live|daily|site verdict=agree|disagree|legacy-unavailable reason= legacyN= ogcN= maxAbsDelta= tsDelta= [ogcQualifiers=]`. Agreement rule: the migration plan's section 5, fixed before any run.
- **Endpoints.** `https://api.waterdata.usgs.gov/ogcapi/v1/collections/`: `continuous` (live, `time=PT{h}H`; history in lake-local calendar-year windows as UTC intervals), `daily` (`statistic_id=00003,32400,30800,00001,00002` for `dv`, or the binding's one statistic), `time-series-metadata` (Primary pick; whether a daily statistic is served), `monitoring-locations/items/USGS-{site}` (`altitude`, `vertical_datum`, `altitude_accuracy`, `site_type_code`). Paged by `rel=next`; more than 20 pages is refused, not truncated.
- **Key.** Optional `USGS_API_KEY`, sent as the `X-Api-Key` header, never in a URL or a log. The Lake Brain job has no access to the secret today; granting it is an IAM change for the owner.
- **Differences handled.** Several series per site and parameter: one series, else the single series marked Primary, else refused (never merged; the gage-height reader refuses more than one). UTC times without fractional seconds. A 200 with zero features is "no data" (an empty year in the history walk); `null` and -999999 values are skipped. A named daily statistic the API does not list as a daily series is refused. A non-JSON body is a failure.
- **Not verified (the session could not reach the host).** That `vertical_datum` uses the same code strings as `alt_datum_cd` (`NAVD88`); that `daily` serves 32400 / 30800 at 10297000, 12393000 and 01314500; the `computation_period_identifier` property name; the `statistic_id` / `qualifier` / `approval_status` property names on `continuous`. The fixtures under `brains/lake/tests/fixtures/usgs-waterdata-v1/` are hand-built, not recordings; record real ones from an allowed runner before `v1` is used.
- **Shadow readiness (review of #228, 2026-11-22).**
  - *Failure reasons.* Every v1 failure carries a code (`rate-limited`, `ambiguous-primary`, `several-series`, `statistic-not-served`, `empty-history`, `html-page`, `non-json`, `http`, `bad-request`, `redirect`, `page-limit`, `metadata-unreadable`, `no-readings`, `unit`, `site-refused`, `unreachable`) and a reason; the shadow line has `reason=ogc-failed:<code>` and `ogcWhy="<reason>"` (quoted, escaped). Every other field value is reduced to `[A-Za-z0-9._:-]`, so a datum string cannot add or fake a field.
  - *Time bound.* The job evaluates up to 3 lakes at a time (`LakeBrainRunOptions.concurrency`, not overridden by the job), each lake's reads one after another, under the Cloud Run task timeout of 60 min (`brains/lake/deploy/deploy-job.sh`); there is no in-process wall-clock limit. In shadow the v1 read runs concurrently with the legacy read; after legacy answers the run waits for v1 at most until 20 s from the read's start (`LAKE_USGS_SHADOW_READ_SECONDS`) and only while a per-run budget of 300 s of such waiting lasts (`LAKE_USGS_SHADOW_BUDGET_SECONDS`); a missed deadline logs `reason=ogc-timeout` and cancels the v1 read. Without `USGS_API_KEY`, 3 or more 429s turn shadow off for the rest of the run. Each "off" is logged once (`[usgs-shadow] shadow-off reason=budget-exhausted|rate-limited-no-key ...`).
  - *Daily statistics.* `dv` asks `daily` for every statistic (legacy asked `dv` without `statCd`) and merges 00003 > 32400 > 30800 > 00001 > 00002, then any other statistic in code order, as legacy did. Each statistic is selected on its own: an ambiguous one is dropped (`ogcDroppedStats=`), the others are kept; only when every statistic is ambiguous is the read refused. A dropped statistic can still show as `missing-dates` or a value difference. `DailyLevel` does not carry the statistic of each date, so the plan's "same statistic per date" check is not made.
  - *Key.* `X-Api-Key` goes only to `https://api.waterdata.usgs.gov`. The v1 client does not follow redirects automatically: it follows them itself and drops the key on a redirect or a `next` link to any other host.
