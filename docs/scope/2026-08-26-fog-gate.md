# Scope — Fog gate (make fog pull the score down)

- **Status:** Proposed (scope only — not yet implemented)
- **Date:** 2026-08-26
- **Repo:** Sector_Engine (shared conditions engine, Cloud Run). iOS + Android both consume it.
- **Trigger:** A night showed "GOOD ALL NIGHT" with hourly bars at 81 while fog was building
  after midnight. The client banner was made fog-aware (iOS PR #193), but the *score itself*
  barely moved — because fog is only a 0.03-weight factor today.

## Problem

Fog **is** already modeled — `HumidityFactor` maps the forecast air–dewpoint spread to a
score: `< 2°F → 45 "Fog likely"`, `< 4°F → 72 "Patchy"`, `< 6°F → 90 "Slight"`, else
`100 "Clear"`. But its aggregation weight is **`humidity = 0.03`** — a deliberate
tie-breaker. So a fog-likely night (45) vs clear (100) moves the blended score by only
`(100−45) × 0.03 ≈ 1.6 points`. An 81 becomes ~79. Invisible.

Yet the factor's own doc says fog *"ends the night — you can't shoot what you can't see, and
you can't run a boat blind."* A thing that ends the night is a **hard limiter**, not a
tie-breaker. It's mis-modeled as a small continuous weight.

## Proposed design — a fog GATE (not a weight change)

Add fog to **`ConditionsGates`** (`Aggregator/ConditionsGates.swift`), the existing hard-cap
layer applied *after* the weighted blend. This is the same pattern the severe-weather /
rain-now / high-wind / cold-water gates already use, and it's the right shape: a great blend
on a fogged-in night gets capped, and the gate's reason surfaces as the binding "why".

**Why a gate, not bumping the 0.03 weight:** raising the weight is blunt and re-tunes the
whole normalization (it also nudges every clear night up). A gate leaves the blend alone on
clear nights and only bites when fog is genuinely likely — matching how fog behaves (a step
change, not a gradient). Consistent with every other "can't fish tonight" signal.

### Graduated caps (mirror the factor's bands)

Driven by `input.fogSpreadF` (the smallest air–dewpoint spread forecast over the window — the
real fog predictor; already on `ConditionsInput`):

| Spread | Meaning | Proposed cap | Rationale |
|---|---|---|---|
| `< fogLikelySpreadF` (≈2°F) | Fog likely on the water | `fogLikelyCap` (≈**35**) | Fog forms → can't shoot / running the boat is dangerous. Hard cap, near blown-out(25)/severe(25). |
| `< fogPatchySpreadF` (≈4°F) | Patchy fog possible late | `fogPatchyCap` (≈**62**) | Still fishable but must never read Prime; soft ceiling. |
| `≥ fogPatchySpreadF` | Slight/none | no gate | The 0.03 factor already handles the slight nudge. |

All four numbers land in `GatesConfig` (see below) so they're **Remote-Config tunable** without
a redeploy — start conservative and tighten from field feedback.

**No-dewpoint fallback:** when `fogSpreadF == nil` (no dewpoint series), keep today's behavior
— the factor's raw-RH path (`RH ≥ 97 → 70`) stays a continuous nudge; the gate does **not**
fire on RH alone (too noisy without the spread). Documented as intentional.

## Why the hourly bars fix themselves (no per-hour work needed)

`ConditionsForecast` builds the night curve so that **"no hour can ever exceed the night's
gauge score — a gate-capped night can never show a green PRIME window"** (Forecast.swift:13-17).
So capping the *night* score via the gate automatically pulls the whole hourly envelope under
the cap. The 81 bars come down; the banner (already fog-aware) and the gauge agree.

**Tradeoff to accept (or refine):** `fogSpreadF` is the *window minimum*, so a night that's
clear until 12A and foggy after still caps the whole night — the early clear hours get pulled
down too. This is exactly how every existing gate behaves (a late high-wind gate caps the whole
night). Accept it for v1. *Optional follow-up:* thread a per-hour spread series and cap per-hour
in the envelope, so early-clear/late-fog nights taper instead of flat-capping — bigger change,
only if field feedback says the flat cap over-penalizes.

## Implementation points

1. **`ConditionsConfig.GatesConfig`** — add, with defaults:
   ```swift
   public var fogLikelySpreadF: Double = 2.0
   public var fogLikelyCap:     Double = 35
   public var fogPatchySpreadF: Double = 4.0
   public var fogPatchyCap:     Double = 62
   ```
2. **`ConditionsGates.evaluate`** — add a block after the rain-now gate:
   ```swift
   if let spread = input.fogSpreadF {
       if spread < g.fogLikelySpreadF {
           hits.append(GateHit(reason: "Fog likely — forms on the water, can't shoot or run the boat",
                               cap: Int(g.fogLikelyCap)))
       } else if spread < g.fogPatchySpreadF {
           hits.append(GateHit(reason: "Patchy fog possible late",
                               cap: Int(g.fogPatchyCap)))
       }
   }
   ```
   (Gate selection already picks the lowest cap as binding, so fog competes with the other gates
   correctly.)
3. **Remote Config** — expose the four knobs through `ConditionsConfigOverrides` /
   `RemoteConfigStore` like the other gate params, so they're tunable live.
4. **No client change.** iOS + Android read the engine's score → both corrected automatically.
   The iOS banner is already fog-aware (PR #193). Web has no conditions surface.

## Tests (`Tests/`)

Add to the gates/aggregator suite:
- Fog-likely night (spread 1.5) → final score ≤ `fogLikelyCap`, binding "why" is the fog gate.
- Patchy (spread 3) → final score ≤ `fogPatchyCap`, not capped to fog-likely.
- Clear (spread 8) → **no** fog gate; score unchanged from today.
- `fogSpreadF == nil`, `RH 98` → no gate (factor-only nudge), score essentially unchanged.
- Fog gate vs a lower gate (e.g. severe warning 25) present together → lower cap binds.

## Rollout / risk

- **Risk:** over-capping humid-but-fishable summer nights (the South is humid; spread can be
  tight without true fog). Mitigation: the thresholds/caps are Remote-Config tunable — ship
  conservative (spread 2°F is genuinely fog-likely) and adjust from reports, no redeploy.
- **Deploy:** engine PR → merge → **Cloud Shell** `cd ~/Sector_Engine && git pull && ./deploy.sh`
  (gcloud isn't on the iOS-dev Mac; Michael deploys). One engine → both apps update with no store
  release.

## Effort

Small — ~1 gate block + 4 config fields + Remote-Config plumbing + ~5 unit tests. A few hours,
then Michael's Cloud Shell deploy.
