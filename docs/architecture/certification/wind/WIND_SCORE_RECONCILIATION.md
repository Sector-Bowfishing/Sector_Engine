## 2. Why 3.1 ≠ 3.3 (code-derived)
Same rubric, same frozen CAL+H1 skill evidence. The only movement is **dimension 8 (freshness/reliability)**, which grew from 0 to 1.33 points as the live archive reached 5 of 30 valid days. Points: direction 4.32 + lead 5.0 + fetch 10.0 + reliability 1.33 + coverage 4.0 + provenance 8.0 = 32.65 → 3.265 → shown 3.3 (3.27 uncapped). Without dim 8: 31.32 → 3.1. Field-validation caps (6.0 / 7.0) are not binding.

They *coexist* because they travel different paths: 3.3 flows scorer → `frozen-scores.json` → orchestrator image → `/scores/wind` (content-compared, stale-guarded), whereas 3.1 is baked into the wind-hourly image and changes only on a wind-hourly redeploy. The stale-score guard HOLDs older or conflicting candidates; `check_score_artifacts.py` (run locally) reports **`wind OK`**.

## 3. Why BWIS 5.4 is separate
A 100-point index of how useful wind information is to a bowfisher (atmospheric skill, fetch, surface, decision, reliability) with its own frozen definition. It does not enter `/scores/wind.value`; it is carried only as `secondary`. It must never be averaged with, ranked against, or displayed as interchangeable with the readiness score.

## 4. Violations of the identity rules (documented, not fixed)
1. `/scores/wind` carries `secondary` (BWIS): rule "every other score type lives inside the Brain's own artifact, never at `/scores/{brainId}`".
2. `/brains/wind.scores` and `/validation/wind.scores` **mirror** scores (3.1 and BWIS): rule "never mirrored into the registry, validation or control nodes". Ops reads the registry copy, so it shows 3.1 where `/scores/wind` says 3.3.
3. `bowfishing_score.py` hard-codes `CERT = 3.1` for display (stale constant); `SCORING.md` still describes Wind as 3.1 FROZEN.
4. No `scoreType`/`scoreRunId`/`scoreScope`.
Fixing these is a **separate approved change** (relabel/move, not recompute): Wind artifact carries BWIS labelled `BWIS`; Ops moves from the registry copy to `/scores/wind`.
